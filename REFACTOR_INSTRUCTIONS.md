# Инструкция для ИИ-агента: рефакторинг и улучшение Whispered

> **Контекст.** Whispered — офлайн-приложение транскрипции на PyQt6 (бэкенд whisper.cpp,
> опциональная диаризация pyannote, локальный LLM через LM Studio). Кодовая база ~12k строк.
> Базовая функциональность работает и покрыта 101 тестом. Цель этой работы — **не новые фичи**,
> а устранение архитектурного долга, багов корректности и проблем качества, выявленных при ревизии.

## Как работать (обязательно к соблюдению)

1. **Ветка:** разрабатывай в `claude/friendly-tesla-vxnm75`. Не пушь в другие ветки.
2. **По одному изменению — один коммит.** Каждый пункт ниже = отдельный коммит с ясным сообщением.
   Не сваливай несвязанные правки в один коммит.
3. **После каждого изменения** запускай `python -m pytest tests/ -v` и `python -m py_compile <изменённые файлы>`.
   Не коммить, если тесты красные.
4. **Не ломай публичные сигнатуры**, пока на них есть вызовы — сначала добавь новое, переведи
   вызовы, потом удали старое.
5. **Покрывай новый чистый код тестами.** Любая новая функция без Qt-зависимостей (парсинг,
   усечение, форматирование, чанкинг) должна получить юнит-тест.
6. **Не пиши комментарии «что делает следующая строка»** — комментарий только для инварианта,
   который код не выражает сам.
7. **Соблюдай очередность приоритетов** P0 → P1 → P2 → P3. P0 — обязательны; P3 — по возможности.

## P0 — Баги корректности (исправить в первую очередь)

### P0.1 — `insights_worker`: запрос к LLM без ограничения размера контекста
- **Файл:** `core/insights_worker.py:53-65` (`_build_prompt_text`).
- **Проблема:** функция склеивает системный промпт + ВСЕ сегменты без усечения. Для записи в
  несколько часов промпт переполняет контекстное окно модели → LM Studio либо обрезает начало
  (теряя инструкции), либо отвечает мусором/None, что всплывает как ложная ошибка «did not respond».
  Сравни с `core/chat_worker.py:27-33`, где транскрипт корректно усекается до `_CONTEXT_CHARS = 48_000`.
- **Форма фикса:** вынести общий помощник усечения (см. P1.4 — `core/llm_text.py: fit_to_context(text, max_chars, marker)`).
  Усекать **только транскриптную часть**, сохраняя системный промпт нетронутым (как в chat_worker:
  усечь до префиксации шаблоном, а не общую строку). Использовать единую константу лимита.
- **Критерий приёмки:** юнит-тест: длинный список сегментов → итоговый промпт не превышает лимит,
  системный промпт присутствует целиком, добавлен маркер усечения.

### P0.2 — `lm_client`: пустой валидный ответ трактуется как сетевая ошибка
- **Файл:** `core/lm_client.py` (конец `chat_completion_stream`, `return "".join(full_text) or None`).
- **Проблема:** при валидном SSE-ответе, где все `delta.content` пусты, `'' or None` → `None`.
  Потребители (`insights_worker`, `chat_worker`) трактуют `None` одинаково как «LM Studio не ответил»,
  хотя сервер ответил корректно. Пользователь видит ложную ошибку соединения.
- **Форма фикса:** различать «сеть/исключение» и «успешный, но пустой ответ». Вариант: возвращать
  `""` (пустую строку) при успешном пустом стриме и `None` только при реальном исключении/URLError;
  потребители тогда отличают пустой результат от обрыва. Согласовать с non-stream методом.
- **Критерий приёмки:** при замоканном стриме с пустыми дельтами потребитель не эмитит ошибку
  соединения.

### P0.3 — `transcriber`: `terminate()` + `join()` без таймаута может подвесить рабочий поток
- **Файл:** `transcriber.py:349-350` и `:391-393`.
- **Проблема:** при отмене процесс whisper.cpp получает SIGTERM, затем `join()` без таймаута.
  Если процесс завис (тяжёлая GPU-работа, игнор сигнала) — рабочий QThread блокируется бессрочно.
  UI это не вешает (это не GUI-поток), но отмена «не срабатывает».
- **Форма фикса:** `join(timeout=N)`; если процесс жив после таймаута — эскалация `kill()` и ещё раз
  `join(timeout=...)`. Залогировать факт принудительного убийства.
- **Критерий приёмки:** ручная проверка отмены; код-ревью на наличие таймаут+kill эскалации в обоих местах.

### P0.4 — `history`: нет WAL/busy_timeout → блокировки между потоком-воркером и UI
- **Файл:** `core/history.py:167-178` (`_connect`).
- **Проблема:** запись в историю (`add`) идёт из рабочих потоков по завершении транскрипции, а UI
  параллельно делает `search`/`list`. SQLite по умолчанию `journal_mode=DELETE` без busy_timeout →
  достижимо `OperationalError: database is locked`. Ретраев нет.
- **Форма фикса:** на каждом соединении выставлять `PRAGMA journal_mode=WAL` и `PRAGMA busy_timeout=<мс>`
  (например 5000). WAL разрешает конкурентные чтения с одним писателем.
- **Критерий приёмки:** тест: конкурентные `add` (из потока) и `search` (из основного) не падают.
  Дополнительно: заменить `datetime.utcnow()` (`history.py:186`, deprecated в 3.12+) на
  `datetime.now(timezone.utc)`.

### P0.5 — `recorder`: импорт numpy и незащищённый RMS в реал-тайм аудио-колбэке
- **Файл:** `core/recorder.py:37-41` (`_rms`), вызывается из `_audio_callback` (~10 Гц) в RT-потоке PortAudio.
- **Проблема:** `import numpy as np` внутри `_rms` исполняется на каждом аудиоблоке в высокоприоритетном
  C-потоке (лишний lookup/биндинг — риск xrun). Плюс `_rms` не обёрнут try/except: неожиданная форма
  `indata` уронит колбэк и порвёт стрим.
- **Форма фикса:** поднять `import numpy as np` на уровень модуля. Обернуть вычисление RMS/эмит в колбэке
  в защитный try/except с логированием, чтобы исключение не доходило до PortAudio.
- **Критерий приёмки:** код-ревью; numpy импортируется один раз; колбэк не пробрасывает исключения.

## P1 — Архитектурный рефакторинг (основная работа)

> Делать инкрементально: каждый под-пункт — отдельный коммит, тесты зелёные после каждого.
> Не пытайся переписать всё разом.

### P1.1 — Декомпозиция god-object `ui/main_window.py` (1137 строк)
`MainWindow` совмещает ~8 ролей: построение UI, хранение состояния, оркестрация транскрипции,
AI-операций, book-пайплайна, батча, экспорт, история, drag&drop/шорткаты.

**Извлечь по слоям (порядок коммитов):**
1. **`state/session.py: Session` (dataclass)** — единое состояние: `current_result`, `cleaned_text`,
   `source_filepath`, `speaker_names`, `mode`. Устраняет разрозненные `_current_*` атрибуты
   (`main_window.py:51-59`). См. P1.2 про двойной источник правды.
2. **`controllers/transcription_controller.py`** — владеет `Transcriber`, ETA-таймингом, потоком
   `_start_transcription / _on_progress / _on_finished / _on_error` (`main_window.py:647-698, 734-762, 849-858`).
   Принимает снапшот настроек, эмитит `progress/finished/error`.
3. **`controllers/ai_controller.py`** — владеет AI-воркером и жизненным циклом `_cleaned_text`
   (`main_window.py:938-1068`).
4. **`controllers/book_controller.py`** — отдельный воркер book-пайплайна (`main_window.py:1072-1136`).
   **Важно:** сейчас AI и book делят один слот `self._ai_worker` — это латентный баг (см. P1.3).
5. **`services/export_service.py` + `ui/export_format_panel.py`** — логика экспорта и чекбоксы форматов
   (`main_window.py:875-934`).
6. **`services/history_service.py`** — сериализация/десериализация результата рядом с `core/history`
   (`main_window.py:780-847`).
7. **`ui/header_settings_bar.py`** (+ виджет `DeviceToggle`, миксин `DragDropMixin`) — модель/язык/режим/
   диаризация. Сейчас `_start_transcription` и `_start_batch_processing` дублируют чтение одних и тех же
   5 контролов (`main_window.py:670-679` и `716-721`) — вынести в `settings_snapshot()`.

**Цель:** `MainWindow` ужать до «построить layout → создать контроллеры/сервисы → связать сигналы →
делегировать», заметно меньше 400 строк.

### P1.2 — Единый источник правды для текущего транскрипта
- **Проблема:** результат живёт в `MainWindow._current_result` И в `TranscriptView._result`
  (`transcript_view.py:90`). Экспорт читает из view (`main_window.py:896`), AI — из окна
  (`main_window.py:956, 1078`). После правок в view состояния могут разойтись.
- **Форма фикса:** `TranscriptView` — это *представление* над `Session`, а не второй стор. Экспорт и AI
  читают результат через один аксессор. **Сбрасывать `cleaned_text` при любой смене результата**, включая
  загрузку из истории (`_load_from_history`, `main_window.py:811-847`) — сейчас сброс только в
  `_start_transcription:664`, из-за чего после загрузки истории «generate» может молча отработать на
  устаревшем cleaned-тексте прошлой записи.

### P1.3 — Базовый класс воркеров `core/base_worker.py: BaseWorker(QThread)`
Сейчас 4 QThread-воркера с разнобоем:

| Аспект | ai_worker | chat_worker | insights_worker | book_batch_worker |
|---|---|---|---|---|
| Флаг отмены | `bool` | `threading.Event` | `threading.Event` | `bool` |
| Done-сигнал | `finished` | `turn_finished` | `finished` | `batch_finished` |
| Error-сигнал | `error` | `error_occurred` | `error_occurred` | `file_error` |
| try/except в run() | есть | **нет** | **нет** | частично |

- **Проблема:** у `chat_worker` и `insights_worker` нет внешнего try/except — необработанное исключение
  в `run()` тихо роняет поток без эмита ошибки. Имена сигналов и идиома отмены несогласованы.
- **Форма фикса:** `BaseWorker(QThread)` с: отменой через `threading.Event` (`cancel()`/`is_cancelled()`),
  шаблонным `run()`, оборачивающим абстрактный `_execute()` в try/except → сигнал `error`, и единым
  набором сигналов (`progress`, `finished`, `error`). Подклассы реализуют только `_execute()`.
  Батч-воркеры сохраняют индекс в payload, но наследуют каркас отмены/ошибок.
- **Отдельный коммит:** дать `AIController` и `BookController` **разные** воркеры (устранить общий слот).
  Добавить guard `if worker and worker.isRunning(): return` перед стартом нового (включая транскрипцию).

### P1.4 — Фасад LLM: схлопнуть дублирование в `core/lm_client.py`
- **Проблема:** `chat_completion` и `chat_completion_stream` дублируют построение payload/запроса/обработку
  ошибок и используют **две разные идиомы отмены** (атрибут `self.is_cancelled` + ThreadPoolExecutor-поллинг
  vs callable-параметр). `ai_worker` лезет в приватные `.lm_client`/`._client` чужих модулей
  (`ai_worker.py:55,70,89,107`) — текущая абстракция. `text_processor`/`article_generator`/`book_pipeline`
  независимо создают клиентов и дублируют `check_connection()`.
- **Форма фикса:** один метод `complete(messages, *, stream, on_token, is_cancelled, temperature, max_tokens)`
  (non-stream = `stream=False`). Единый контракт отмены (callable-параметр; убрать атрибут-идиому и
  ThreadPoolExecutor-поллинг). Один канонический текст ошибки «не отвечает» (сейчас переписан в
  `chat_worker.py:82-87` и `insights_worker.py:109-113`). Клиент инжектится в воркеры, а не создаётся
  внутри `run()` и не достаётся из под-объектов.

### P1.5 — Унификация каталога данных
- **Проблема:** приложение пишет под ДВА корня: `~/.whisper-fedora/` (`history.py:21`, `recorder.py:34`,
  `config.py:18`) и `~/.local/share/Whispered/`/XDG (`logger.py:18-28`).
- **Форма фикса:** единый помощник `data_dir()` (одна функция, XDG-совместимая), все модули берут пути
  из него. Учесть миграцию: если существует старый каталог — продолжать читать оттуда или перенести.
