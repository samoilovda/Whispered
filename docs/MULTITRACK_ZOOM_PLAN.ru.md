# Мультитрековые записи Zoom: план реализации и методика оценки

Статус: черновик задания для ИИ-агента (2026-08-21). Не выполнено.
Владелец решения: пользователь. Агент выполняет шаги M0…M7 по порядку,
останавливаясь на гейтах, помеченных **STOP**.

---

## 0. TL;DR для агента

Zoom умеет писать «Record separate audio file for each participant»: рядом с
общим миксом кладётся папка `Audio Record/` с отдельным файлом на каждого
участника. Задача: научить Whispered принимать такую папку, транскрибировать
каждую дорожку отдельно и склеивать результат в один `TranscriptionResult` с
достоверными метками спикеров — без диаризации.

Но **сначала измерение, потом продукт**: шаг M0–M1 строит бенчмарк и отвечает
на вопрос «даёт ли мультитрек выигрыш». Только при положительном ответе
(критерии в §6.5) переходим к интеграции в UI.

Тестовый материал уже лежит в репозитории:
`input/Кастдев Clarus Роман Атри/` (кастдев по продукту, ru, 2 участника,
38 минут).

## 1. Формат Zoom: проверенные факты об образце

Измерено через `ffprobe`/`ls` 2026-08-21, не додумано:

```
input/Кастдев Clarus Роман Атри/
├── recording.conf                        126 B
├── audio1857894770.m4a                    25 MB   ← общий микс (baseline)
├── video1857894770.mp4                   284 MB
└── Audio Record/
    ├── audioDen11857894770.m4a            ← дорожка участника «Den», индекс 11
    └── audioТонкиеМа21857894770.m4a       ← дорожка участника «ТонкиеМа», индекс 21
```

`recording.conf` — это JSON в одну строку:

```json
{"magic_number":"857894770","items":[{"process":100,"audio":"audio1857894770.m4a","prefix":"","video":"video1857894770.mp4"}]}
```

Параметры потоков:

| Файл | codec | sr | ch | duration | bitrate |
|---|---|---|---|---|---|
| `audio1857894770.m4a` (микс) | aac | 48000 | 2 | 2305.003 s | 90 kbps |
| `Audio Record/audioDen1…` | aac | 48000 | 2 | 2304.981 s | 51 kbps |
| `Audio Record/audioТонкиеМа2…` | aac | 48000 | 2 | 2304.981 s | 47 kbps |

Выводы, на которые опирается реализация:

1. **Дорожки выровнены по нулю.** Длительности совпадают бит-в-бит между
   собой и отличаются от микса на 22 мс. Значит общий `t=0` — общий, и
   ресемплинг/сдвиг на старте не нужен. Проверять это утверждение агент
   обязан на каждом новом наборе (§5.1), а не принимать на веру.
2. **Имя участника закодировано в имени файла.** Схема:
   `audio` + `<display_name>` + `<index>` + `<magic_number>` + `.m4a`,
   где `magic_number` берётся из `recording.conf`. Разбор: отрезать префикс
   `audio`, отрезать известный `magic_number` с конца, затем отрезать
   хвостовые цифры — это индекс участника, остаток — имя.
3. **Zoom режет display name.** «Тонкие Ма…» — обрезка исходного имени и
   удаление пробелов. Имя пригодно как *подсказка*, но UI обязан позволять
   переименовать спикера (`TranscriptionResult.speaker_names` уже это умеет).
4. Имена содержат кириллицу → все пути обрабатывать как `pathlib.Path`,
   без предположений об ASCII и без нормализации Unicode «на глазок»
   (macOS отдаёт NFD — сравнение имён делать через `unicodedata.normalize`).

## 2. Гипотеза, которую проверяем

**H1 (атрибуция).** Мультитрек даёт долю правильно атрибутированных слов
существенно выше, чем pyannote-диаризация поверх микса — потому что
принадлежность дорожки известна из формата, а не выводится.

**H2 (точность текста).** На перекрывающейся речи (перебивания, поддакивания)
мультитрек восстанавливает слова, которые в миксе теряются или сливаются.

**H3 (риск).** Отдельная дорожка на 60–80 % состоит из тишины и содержит
подмешку голоса собеседника (bleed через открытые колонки). Наивная подача
такой дорожки в whisper.cpp даёт: (а) галлюцинации на тишине, (б) дубли
чужой речи. Без обработки (§5.2, §5.3) мультитрек может оказаться **хуже**
микса по WER, выиграв только по атрибуции.

H3 — основная причина, по которой бенчмарк делается до продуктовой обвязки.

## 3. Архитектурные ограничения

Обязательны правила `CLAUDE.md`; ниже — то, что специфично для этой задачи.

- **Слои.** Разбор папки и модель дорожек — Qt-free, в `domain/multitrack.py`
  (по образцу `domain/course_capture.py`). Оркестрация «N дорожек → один
  результат» — в `application/multitrack_session.py`. Ввод-вывод аудио
  (декодирование, нарезка) — в `core/`. UI трогаем последним шагом.
  `tests/test_domain_transcription.py` уже запрещает `domain/` импортировать
  PyQt6 — новый модуль должен проходить этот запрет.
- **Никакого блокирования UI.** N дорожек — это N последовательных прогонов
  whisper.cpp. Прогон идёт в дочернем процессе (`transcriber.py`), очередь —
  в `QThread` через `core.worker_registry.WorkerRegistry`. Отмена обязана
  прерывать текущую дорожку и всю очередь.
- **`word_timestamps` остаётся `False`.** В `CLAUDE.md` зафиксировано, что
  `True` ломает кириллицу склейкой слов (`_group_words_into_segments`).
  Слияние дорожек проектируем на сегментных таймингах, не на пословных.
- **Офлайн.** Никаких облачных ASR для сравнения. Эталон делает человек.
- **Config.** Новые поля с дефолтами: `multitrack_enabled: bool = True`,
  `multitrack_silence_threshold_db: float = -35.0`,
  `multitrack_min_speech_ms: int = 400`,
  `multitrack_bleed_suppression: bool = True`.
- **Один шаг — один коммит**, префиксы `feat:`/`fix:`/`test:`/`docs:`.

Что переиспользовать, а не писать заново (подсистема Live уже решает
близкую задачу «два источника → одна лента»):

| Нужда | Готовый модуль |
|---|---|
| Детекция речи по источнику | `core/live/vad.py` (`EnergyVAD`, `PerSourceVAD`, `pcm_rms`) |
| Подавление дубля одной фразы в двух источниках | `core/live/echo_detector.py` (`EchoDuplicateDetector`, `normalize_text`) |
| Сборка перекрывающихся реплик в одну ленту | `core/live/overlap_timeline.py` (`LiveOverlapTimeline`, `SourceSpeakerLabels`) |
| Проверка расхождения часов между источниками | `core/live/clock_aligner.py` (`DriftReport`) |
| Схлопывание мелких сегментов | `transcriber.py::_coalesce_batch_segments` |

Если модуль Live не подходит один-в-один — выносим общую часть, а не копируем.

## 4. Шаги работ

### M0. Бенчмарк-каркас (до любого продуктового кода)

Создать `tools/bench_multitrack.py` — standalone CLI (в нём `print()` разрешён
правилом 5, обязателен `if __name__ == "__main__"` из-за spawn).

Что делает:
- принимает папку записи Zoom и список режимов (`mixed`, `mixed+diar`,
  `multitrack`);
- прогоняет транскрипцию каждым режимом с зафиксированными параметрами
  (модель, язык `ru`, `n_threads`, `use_gpu`) и сохраняет сырые результаты в
  `output/bench/multitrack/<UTC-timestamp>/<mode>.json`
  (сериализация — уже существующая в `exporters.py`);
- пишет `run.json` с окружением: версия модели, коммит, CPU/GPU, wall-clock,
  RTF, пиковая RSS.

**DoD:** `python tools/bench_multitrack.py --help` работает; повторный запуск
режима `mixed` даёт побайтово совпадающий JSON (детерминизм подтверждён —
если нет, зафиксировать это в отчёте и учитывать шум при сравнении).

### M1. Разбор папки Zoom (`domain/multitrack.py`)

```python
@dataclass(frozen=True)
class TrackSpec:
    path: Path
    display_name: str      # "Den"
    participant_index: int # 1
    duration: float

@dataclass(frozen=True)
class MultiTrackRecording:
    root: Path
    mixed_audio: Path | None
    video: Path | None
    tracks: tuple[TrackSpec, ...]
    magic_number: str
```

- `detect_multitrack(path) -> MultiTrackRecording | None` — принимает папку
  ИЛИ файл внутри неё; отсутствие `recording.conf` или `Audio Record/` →
  `None` (не исключение, это нормальный «обычный файл»).
- Разбор имени — отдельная чистая функция `parse_track_filename(name, magic)`,
  покрытая таблицей кейсов: кириллица, имя с цифрой на конце («User2» →
  индекс 2, имя «User»… — задокументировать, что такой кейс неразрешим, и
  выбрать поведение), отсутствующий индекс, одна дорожка, 9+ дорожек.
- Никаких `ffprobe`-вызовов в `domain/` — длительность передаётся снаружи.

**DoD:** `tests/test_domain_multitrack.py` зелёный; `mypy` чистый; модуль не
импортирует Qt.

### M2. Речевые окна по дорожке (`core/multitrack_audio.py`)

Ключевой шаг против H3(а). На вход — дорожка, на выход — список интервалов
речи `[(start, end), …]` и вырезанные из них WAV-фрагменты.

- Декодирование через ffmpeg в 16 kHz mono WAV (переиспользовать
  `transcriber.py::_convert_to_wav`, при недоступности ffmpeg — существующая
  ошибка `FFmpegUnavailableError` с подсказкой из `core/external_tools.py`).
- Детекция речи: сначала попробовать `EnergyVAD`/`pcm_rms` из
  `core/live/vad.py` по кадрам; сравнить с `ffmpeg -af silencedetect` как
  альтернативой и выбрать по метрике «доля пропущенной речи» на эталонном
  фрагменте. Решение обосновать числами в отчёте.
- Склейка: интервалы ближе `merge_gap` (по умолчанию 0.6 с) объединяются;
  окна короче `multitrack_min_speech_ms` отбрасываются; к каждому окну
  добавляется контекстный запас 0.3 с с обеих сторон (whisper.cpp плохо
  работает с обрезанными на слове границами).
- Транскрибируются **только** окна, тайминги возвращаются в абсолютную шкалу
  дорожки прибавлением offset окна.

**DoD:** на образце покрытие речи на дорожку выведено в отчёт (ожидаемо
20–50 % от 2305 с); суммарное аудио, поданное в whisper, сократилось
пропорционально; тесты на синтетическом PCM (тишина/тон/тишина).

### M3. Подавление подмешки чужого голоса (H3(б))

Дорожка участника может содержать голос собеседника (акустический возврат).
Признаки, по которым фрагмент считается «не свой»:
- временное перекрытие ≥ 50 % с речевым окном другой дорожки, И
- нормализованный текст совпадает с текстом другой дорожки
  (`core.live.echo_detector.normalize_text` + расстояние по словам), И
- средняя энергия окна ниже энергии этого же интервала на другой дорожке
  (в дБ; порог настраиваемый).

Побеждает дорожка с большей энергией; проигравший фрагмент удаляется, факт
логируется и попадает в метрику `bleed_suppressed_seconds`. Правило
«совпадение только по времени» использовать **нельзя** — это убьёт настоящие
перебивания, которые мы как раз хотим сохранить (H2).

**DoD:** unit-тесты на 4 случая: чистое перебивание (обе реплики остаются),
явная подмешка (одна удаляется), одинаковый текст без перекрытия (обе
остаются), перекрытие с разным текстом (обе остаются).

### M4. Сборка одного `TranscriptionResult`

- Сегменты всех дорожек сортируются по `start`; `Segment.speaker` — стабильный
  id вида `track_1`, `track_2`; `TranscriptionResult.speaker_names` —
  `{"track_1": "Den", …}` из имён файлов. Так переименование в UI и все
  экспортёры (`exporters.py::_speaker_name`) работают без изменений.
- `duration` = max по дорожкам; `language` — из первой дорожки, при
  расхождении между дорожками — предупреждение в лог и выбор по большинству.
- Перекрывающиеся сегменты разных спикеров **не** сливаются и не сдвигаются:
  SRT/VTT это допускают, а таймлайн `LiveOverlapTimeline` уже описывает
  поведение — свериться с ним, чтобы Live и файловый режим вели себя одинаково.

**DoD:** `tests/test_multitrack_merge.py`; экспорт в txt/srt/vtt/json на
собранном результате не падает и содержит имена спикеров.

### M5. **STOP** — прогон бенчмарка и решение

Выполнить §6 целиком, положить отчёт в
`output/bench/multitrack/<timestamp>/report.md` и вынести вердикт по §6.5.
Дальше не идти без явного «да» от пользователя.

### M6. Продуктовая обвязка (только после M5)

- `application/multitrack_session.py`: очередь дорожек, агрегированный
  прогресс (`дорожка i из N` + процент внутри дорожки), отмена, передача
  собранного результата в существующий `DocumentSession.apply_result()`.
- `ui/file_selector.py`: приём папки через drag&drop и кнопку «выбрать
  папку»; при обнаружении мультитрека — плашка «Найдено N дорожек: Den,
  Тонкие Ма…» с переключателем «использовать раздельные дорожки / общий микс».
- `ui/transcribe_options.py`: при выбранном мультитреке диаризация
  автоматически выключается и объясняется почему (спикеры уже известны).
- `batch_processor.py`: папка Zoom как один элемент очереди, не N файлов.

**DoD:** `tests_qt/test_multitrack_panel.py` (реальный Qt, offscreen);
`WorkerRegistry` держит воркеры; `MainWindow.closeEvent` гасит очередь.

## 5. Обязательные проверки перед доверием формату

### 5.1 Выравнивание дорожек

Перед слиянием агент обязан проверить, а не предположить:
- длительности дорожек отличаются ≤ 100 мс друг от друга;
- взаимная корреляция огибающих энергии двух дорожек на первых 120 с даёт
  пик в |lag| ≤ 100 мс.

Если проверка не проходит — оценить сдвиг корреляцией и применить его как
константный offset, а факт коррекции записать в отчёт. Дрейф часов (растущий
сдвиг) — стоп-сигнал: конструкция §4 его не покрывает,
`core/live/clock_aligner.py` показывает, чего это стоит.

### 5.2 Тишина

Доля тишины на дорожку и число сегментов, выданных whisper внутри интервалов,
помеченных VAD как тишина. Второе число в идеале 0; > 0 означает, что
галлюцинации всё ещё проходят и порог VAD надо ужесточать.

### 5.3 Подмешка

Доля секунд, где обе дорожки одновременно «говорят», и какая часть из них
классифицирована как подмешка, а какая как настоящее перебивание. Ручная
выборочная проверка 20 случаев обязательна перед вердиктом.

## 6. Методика оценки

### 6.1 Сравниваемые режимы

| Режим | Что | Роль |
|---|---|---|
| **A** | `audio1857894770.m4a`, без диаризации | база «как сейчас чаще всего» |
| **B** | тот же микс + pyannote (`diarizer.py`, `num_speakers=2`) | честный конкурент по атрибуции |
| **C** | мультитрек по §4 | кандидат |
| **C-naive** | мультитрек без VAD-гейта и без §3 | контроль: показывает вклад обработки |

Все режимы — одна модель, один язык (`ru`), один `initial_prompt` (пустой),
`word_timestamps=False`, одна машина, прогоны последовательно (правило
«не бить LM Studio/ASR параллельными запросами»).

### 6.2 Эталон

Полный эталон на 38 минут делать не нужно и дорого. Берём **три фрагмента по
4 минуты** (12 минут ≈ 31 % записи), выбранных так:
1. начало — знакомство, спокойная очередь реплик;
2. середина — участок с максимальной долей одновременной речи (агент находит
   его автоматически по пересечению VAD-окон двух дорожек);
3. конец — участок с наибольшей плотностью терминов/имён собственных.

Агент готовит заготовку эталона (лучший из режимов + разметка спикеров) в
`output/bench/multitrack/<ts>/reference_draft.md` с таймкодами, **человек
вычитывает и правит**. Это единственный ручной шаг во всей методике; без него
метрики 6.3.1–6.3.3 недоступны, и агент обязан сказать об этом прямо, а не
подменять эталон выводом другой модели.

Формат эталона — простой, редактируемый вручную:
```
[00:12:31.4] Den: и вот тут я обычно застреваю
[00:12:33.0] Тонкие Ма: а что именно не получается
```

### 6.3 Метрики

Метрики с ✱ считаются без эталона — их можно гонять на всех 38 минутах и на
любых новых записях в авторежиме.

**6.3.1 WER / CER** (на фрагментах эталона)
Нормализация перед сравнением: нижний регистр, убрать пунктуацию, `ё`→`е`,
числа привести к словесной форме, убрать филлеры-однословки из
фиксированного списка. Считать по стандартному Левенштейну на словах.
Отдельно: WER на всей выборке и WER только на неперекрывающейся речи.

**6.3.2 Точность атрибуции спикера** (на фрагментах)
Доля слов эталона, у которых предсказанный спикер совпал с эталонным, при
оптимальном сопоставлении меток (венгерский алгоритм на 2×2 — тривиально).
Для A метрика неопределена (спикеров нет) → фиксируем как 0 и оговариваем.
Дополнительно — матрица ошибок и `speaker_switch_error` (число ложных смен
спикера на минуту).

**6.3.3 Восстановление перекрытий** (на фрагментах)
В эталоне пометить слова, произнесённые в интервалах одновременной речи.
Метрика — recall этих слов по режимам. Прямой тест H2.

**6.3.4 ✱ Галлюцинации**
- `silence_hallucination_seconds`: суммарная длительность сегментов, целиком
  попавших в VAD-тишину своей дорожки (для A/B — в тишину микса);
- `loop_ratio`: доля сегментов, где один и тот же 3-грамм повторяется ≥ 3 раз;
- `duplicate_ratio`: доля соседних сегментов с нормализованным текстом,
  совпадающим более чем на 90 %.

**6.3.5 ✱ Покрытие**
`speech_seconds_transcribed / vad_speech_seconds` и слов на минуту речи.
Резкое падение относительно A означает, что VAD-гейт съедает речь — это
провал, даже если WER выглядит хорошо.

**6.3.6 ✱ Термины**
Список из 15–25 терминов кастдева (названия продукта, имена, жаргон),
составляется один раз человеком или извлекается LLM из транскрипта A и
подтверждается человеком. Метрика — сколько терминов найдено и сколько раз,
плюс список «почти совпадений» (расстояние 1–2) как индикатор искажений.

**6.3.7 ✱ Стоимость**
Wall-clock, RTF (`wall_clock / 2305`), сколько секунд аудио реально подано в
ASR, пиковая RSS, число прогонов whisper. Для C ожидается рост числа прогонов
(N дорожек), но падение поданных секунд за счёт VAD — обе величины в отчёт.

**6.3.8 ✱ Согласие режимов** (без эталона, для полной длины)
Выровнять A и C по времени, посчитать долю совпавших нормализованных слов и
выдать топ-20 расхождений с таймкодами. Это не метрика качества, а
инструмент: она показывает человеку, куда смотреть, и позволяет прогонять
диагностику на новых записях без эталона вовсе.

**6.3.9 Польза на выходе (вторично)**
Прогнать существующие промпты (`prompts/`, инсайты) на транскриптах A и C,
сравнить: число извлечённых инсайтов, доля инсайтов с корректной атрибуцией
реплики спикеру, число фактических ошибок при ручной проверке 10 инсайтов.
Метрика шумная (LLM недетерминирован) — идёт в отчёт как наблюдение, а не
как критерий приёмки.

### 6.4 Формат отчёта

`output/bench/multitrack/<UTC-ts>/`:
- `metrics.json` — все числа машиночитаемо, с полем `has_reference: bool`;
- `report.md` — таблица «метрика × режим», вердикт, топ-20 расхождений,
  список ручных проверок, которые человек ещё должен сделать;
- `<mode>.json` — сырые результаты;
- `reference_draft.md` / `reference.md`.

В отчёте обязательно: версия модели, коммит, железо, дата, длительность
прогонов. Отчёт без этих полей считается недействительным.

### 6.5 Критерии приёмки (гейт M5)

Мультитрек признаётся успешным, если **одновременно**:

1. **Атрибуция** (6.3.2): C ≥ 95 % и C − B ≥ +10 п.п. абсолютных.
   Это главный критерий; ради него всё и делается.
2. **Текст не хуже** (6.3.1): WER(C) ≤ WER(A) + 1.0 п.п. абсолютных.
   Мультитрек имеет право не выиграть по WER, но не имеет права проиграть
   заметно.
3. **Перекрытия** (6.3.3): recall(C) − recall(A) ≥ +15 п.п.
   Если этот пункт не выполнен, H2 опровергнута — фиксируем это честно.
4. **Галлюцинации** (6.3.4): `silence_hallucination_seconds(C)` ≤
   `silence_hallucination_seconds(A)`; `loop_ratio(C)` ≤ `loop_ratio(A)`.
5. **Покрытие** (6.3.5): ≥ 0.98 от покрытия A.
6. **Стоимость** (6.3.7): RTF(C) ≤ 2.0 × RTF(A). Выше — режим остаётся, но
   только как явный выбор пользователя, не как автоматический.

Исходы:
- все 6 → идём в M6, режим включается автоматически при обнаружении папки;
- 1 выполнен, 2–5 выполнены, 6 нет → M6, но режим по умолчанию выключен;
- 1 не выполнен → мультитрек не даёт того, ради чего затевался: отчёт,
  архив плана, остановка;
- 2 или 4 не выполнены → вернуться в M2/M3, это дефект обработки, а не
  формата; после двух неудачных итераций — остановка и отчёт.

Дополнительно всегда сравнить C с **C-naive**: если разница мала, значит
VAD-гейт и подавление подмешки не нужны и код надо упростить.

## 7. Что агент делает в авторежиме, а что нет

**Делает без человека:**
- всё в M0–M4, включая тесты и гейты `ruff`/`pytest`/`mypy`/`compileall`;
- полный прогон A/B/C/C-naive и все метрики с ✱ на 38 минутах;
- поиск фрагментов для эталона, генерацию `reference_draft.md`;
- диагностику 5.1–5.3 и отчёт;
- откат к предыдущему шагу, если гейт §6.5 указал на дефект обработки.

**Останавливается и спрашивает:**
- перед M6 (гейт M5) — всегда;
- когда нужен вычитанный эталон (метрики 6.3.1–6.3.3 без него не считаются
  — выдать отчёт с `has_reference: false` и явно сказать, каких выводов
  сделать нельзя);
- при провале проверки выравнивания 5.1 с признаками дрейфа часов;
- если для новых записей потребуется формат, отличный от разобранного в §1.

**Не делает никогда:**
- не подменяет эталон выводом любой модели и не называет такое сравнение
  «WER»; сравнение двух машинных транскриптов — это метрика 6.3.8, у неё
  другое имя и другой смысл;
- не подкручивает пороги VAD «под метрику» после того, как увидел результат
  на фрагментах эталона: пороги фиксируются на первом фрагменте, метрики
  считаются на остальных двух;
- не удаляет и не перезаписывает файлы в `input/` — только чтение;
- не отправляет аудио и транскрипты никуда за пределы машины.

## 8. Риски

| Риск | Признак | Реакция |
|---|---|---|
| Дорожки не выровнены на других записях | 5.1 не проходит | константный offset; при дрейфе — стоп |
| Bleed съедает настоящие перебивания | recall перекрытий (6.3.3) у C ниже, чем у C-naive | ослабить §3, оставить только энергетический критерий |
| VAD режет тихую речь | покрытие (6.3.5) < 0.98 | понизить порог, увеличить контекстный запас окна |
| N дорожек × время = слишком долго | RTF > 2× | не включать по умолчанию; показать оценку времени в UI до старта |
| Zoom-конференция на 8 участников | 8 прогонов ASR | ограничить: при > 4 дорожек предупреждать и предлагать микс |
| Имя участника не парсится | пустое `display_name` | fallback `Участник N`, переименование в UI |
