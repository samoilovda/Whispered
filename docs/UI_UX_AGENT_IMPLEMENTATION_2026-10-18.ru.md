## 3. Инварианты, которые нельзя потерять

- **Локальный режим по умолчанию.** Облачный провайдер сейчас разрешён только для YouTube-пакета по пользовательской настройке. Readiness, preview, импорт, экспорт и открытие записи не запускают генерацию/публикацию сами. Добавление Ollama в N05 — отдельное явное расширение локальных интеграций, с обновлением контрактов и документации; не расширение облачной передачи.
- **Две колонки:** библиотека и центр. В центре Start / Run / Record / Cover. Материалы остаются вкладками записи, без нового хаба и постоянного третьего инспектора.
- **Один исполнитель генерации:** реестр `application.steps.STEP_REGISTRY` → `JobEngine` → `ui.job_runner.JobRunner`. Существующие single-step действия тоже идут этим путём. Новый UI переиспользует его; собственные параллельные генераторы запрещены.
- **Направление зависимостей:** `domain` — чистые DTO/правила, без Qt и верхних слоёв; `application` — координация, без UI; `infrastructure` — IO-адаптеры; `core` не импортирует `application/ui`. Расположение существующего HistoryStore в `core` сохранять до отдельного обоснованного рефакторинга.
- **Долгие операции не блокируют GUI.** Больше ~100 мс — worker/process; Qt-сигналы, отмена, `WorkerRegistry`, контроль жизненного цикла. Не добавлять `wait()`/сетевые вызовы в обработчик кнопки.
- **Идентичность записи.** Async-задание фиксирует `record_id`, revision и generation/session token при запуске. Ни один late result не применяется к «текущему» record без проверки. Одинаковый текст не означает одинаковую запись.
- **Пользовательская правка отдельно от генерации.** Манифест описывает модельный результат; overlay/редакционная версия описывает изменения пользователя. Не портить content digest и не сбрасывать ручные правки при regen.
- **Совместимость.** Сохранить `v2:` transcript revision, валидацию артефактов, атомарные записи и правила отмены из предыдущего аудита. Отсутствующий/неизвестный/повреждённый материал не выдавать за свежий.
- **Сохранить текущую публикацию.** private/unlisted, утверждённый пакет, проверка pending fingerprint и повторной загрузки; не превращать upload в автоматический шаг рецепта.
- **Не включать `word_timestamps=True` по умолчанию:** известна проблема кириллицы. Субтитры и клипы первой версии работают на сегментных временах.
- **RU/EN и доступность.** Строки через `tr`, `Retranslator`, русские plural forms; язык меняется без перезапуска. Статус имеет текст, не только цвет. Изменение темы обновляет семантические цвета.

## 4. Общие контракты состояния и хранения

Это предлагаемые структуры, а не описание существующих API. Названия можно уточнять при реализации, сохраняя поведение. Не вводить все структуры заранее: добавлять по мере задач.

### 4.1. Завершение редактирования перед переходом

Предлагаемый application-контракт `prepare_leave(record_id, reason) -> LeaveDecision`:

```text
clean → allow
dirty → validate → persist draft/result + revision for captured record_id
                     ├─ success → allow, publish committed result to consumers
                     └─ error   → stay, preserve buffer, show retry/details
```

Если запись асинхронная, UI получает `pending`; последний запрос перехода ставится в управляемую очередь, не выполняется до успешного сохранения. Новый результат не применяется до durable commit. При закрытии окно откладывает закрытие до завершения/явного выбора, без долгой блокировки GUI. Невалидный буфер не исправляется молча. Для аварийного восстановления хранить draft отдельно от принятой ревизии. Debounce должен захватывать ID записи; flush на границе перехода не должен записать A в B.

### 4.2. Персистентное состояние записи

Предпочтительно расширять существующий SQLite HistoryStore версионированными миграциями:

| Объект | Минимальные поля / правила |
|---|---|
| Редакторский draft | `record_id`, `base_revision`, формат/буфер, `updated_at`, schema version; принятая ревизия остаётся отдельно |
| Монтаж | `record_id`, `transcript_revision`, список интервалов/anchors, версия схемы, `updated_at`; состояния `current / needs_review` |
| Беседа | conversation ID, `record_id`, source revision, provider/model snapshot; сообщения со стабильным порядком и `complete / cancelled / failed` |
| Состояние вычитки | `record_id`, revision, anchor, `unreviewed / reviewed / flagged`; правка сегмента инвалидирует отметку при необходимости |
| Очередь | batch ID, item ID, source reference, recipe/params snapshot, run ID, состояние; незавершённое `running` после crash становится `interrupted` |

Сгенерированные файлы и overlays продолжать хранить существующим способом в `artifact_dir`. Не создавать вторую конкурирующую базу истории. Пользовательские данные внутри конфигурации глобальных настроек не хранить.

Миграции: backup перед изменением схемы, транзакция, идемпотентность, тест на предыдущую БД, откат при ошибке. Удаление истории должно транзакционно учитывать новые дочерние строки. Не менять существующую политику хранения внешних файлов без отдельного видимого действия. Неизвестная версия пользовательского состояния сохраняется и обозначается как неподдерживаемая, а не перезаписывается пустым объектом.

### 4.3. Монтажные anchors и ревизии

В MVP anchor содержит временной диапазон, speaker ID и fingerprint исходного текста плюс базовую revision. Само хранение индекса сегмента недостаточно. При неизменном времени/идентичности разрешён однозначный перенос; при split/merge или нескольких возможных совпадениях — `needs_review`, сохранение исходного решения и явный выбор пользователя. Не пытаться «угадать» новый монтаж и сразу экспортировать его.

### 4.4. Готовность и экспорт

`StepReadiness` должен различать шаг, провайдера, состояние `ready / checking / needs_setup / unavailable`, причину, действие исправления и категорию передаваемых данных. `key_present` отдельно от `connection_verified`. Проверка ASR не зависит от состояния LLM.

`ExportPlan` — immutable snapshot записи/revision/overlays и выбранных выходов. Каждый выход: назначение, формат, источник, freshness `current / stale / unknown / missing`, ожидаемый путь, решение о конфликте. Выполнение читает этот snapshot; при изменении данных до старта предлагает обновить план. Preview и export используют одну функцию композиции пользовательского результата.

Существующий 9:16 cover-brand gate не считать автоматически закрытым работой над видеоклипами.

### N08 / F-08. Live presentation

**Точки:** `ui/live_view.py`, `ui/live_transcript_view.py`, `ui/live_session_controller.py`, `core/live/`; [действующие Live gates](LIVE_TRANSCRIPTION_PLAN.ru.md).

**MVP:** дополнительное окно с крупным текстом, маркировкой partial/final, источником, состоянием recording/paused/stopped и клавиатурным управлением. Оно подписывается на существующую session pipeline, не создаёт вторую запись/ASR. Закрытие presentation-window не завершает запись неожиданно; отдельное явное действие stop.

**Приёмка:** частичные обновления не дублируют final, pause/resume/device loss/disconnect восстанавливаются понятно, финальный transcript совпадает с сохранённым. Нагрузочный прогон с реальным микрофоном/моделью и матрица Zoom/Meet/Teams из Live-плана обязательны для включения по умолчанию. Без аппаратуры можно завершить код/симуляции, но статус остаётся `blocked_validation`, flag выключен.

## 9. Общая матрица приёмки и проверки

### Для каждого затронутого сценария

| Измерение | Обязательные варианты |
|---|---|
| Запись | Новая, старая, без медиа, два record с одинаковым текстом, длинный transcript |
| Состояние | Empty, loading, ready, partial, failed, cancelled, stale/unknown, восстановление после restart |
| Данные | RU/EN/Unicode, длинный заголовок, missing/corrupt artifact, версия схемы до миграции |
| UI | RU/EN live switch, dark/light, 900×550/1100×700/1440×900, text scaling |
| Навигация | Библиотека, Ctrl+K, меню, новая запись, close, смена вкладки, late worker result |
| IO | Permission denied, disk-full simulation, отмена, source moved, existing export target |

Функциональные проверки делать на наблюдаемом контракте, а не на совпадении реализации самой с собой. Для scheduler/streaming пользоваться barriers/events/fake transports, а не случайными sleep. Qt-stubs не доказывают порядок сигналов, фокус или lifetime QThread: для этого нужны `tests_qt`.

### Команды gate

Использовать Python 3.11 и установленные lock-файлы. Для одного исправления сначала узкие тесты; полный gate один раз на завершённый логический набор и повторно при последующих существенных изменениях. Не переустанавливать среду без необходимости.

```bash
# В корне checkout; system Python запускает unit suite с Qt stubs.
ruff check .
python -m pytest tests/ -q
python -m compileall -q . -x '.venv|.claude|build|dist|docs/archive'

# Реальные Qt-типы/виджеты — только проектный venv.
.venv/bin/python -m mypy --ignore-missing-imports core/ transcriber.py diarizer.py \
    exporters.py utils.py config.py version.py domain/ application/ infrastructure/ \
    batch_processor.py book_pipeline.py ui/
QT_QPA_PLATFORM=offscreen .venv/bin/python -m pytest tests_qt/ -q
QT_QPA_PLATFORM=offscreen XDG_DATA_HOME=/tmp/whispered-uiux-gallery-data \
    .venv/bin/python tools/render_ui_gallery.py --check \
    --output /tmp/whispered-uiux-gallery
git diff --check
```

Новые каталоги `domain/application/infrastructure` также типизируются и проходят import-layer tests. Если меняются упаковка/ресурсы — build/smoke соответствующей платформы; для migrations — round-trip/rollback fixtures; для новых зависимостей — lock и SCA. Документационные изменения сами по себе не требуют повторять длительные аппаратные тесты.

### Критерий завершения этапа

Этап принят, когда его наблюдаемые сценарии и миграции проверены, нужные screenshots просмотрены, локализация и документация актуальны, а оставшиеся аппаратные/провайдерские ограничения явно отделены. Фраза «тесты зелёные» без имени набора/числа/окружения недостаточна. Не переиспользовать числа тестов старого аудита как результаты нового запуска.

## 10. Формат отчёта агента

После каждого логического набора обновлять журнал кратко:

```text
ID: T05
Статус: accepted / code_complete / blocked_validation
Проблема и поведение после изменения: ...
Файлы/commit: ...
Миграция и совместимость: ...
Проверки: команды, exit status, counts; ручные сценарии и снимки
Не выполнено: конкретный критерий и фактическая причина
Следующая доступная задача: ...
```

В итоговом сообщении указывать выполненные T/N-ID, заметное пользователю поведение, миграции и ограничения. Отдельно перечислить аппаратные gates и неподтверждённые гипотезы. Новые функции из M3/M4 не должны скрывать оставшиеся дефекты M1, а реализация предложения не означает, что его полезность уже подтверждена пользователями.
