# Часть A. Решения по «сделано нелогично»

## A1. `_current_result` присваивается в трёх местах — `S`

**Проблема.** `DocumentSession.apply_result()` заводили ровно для того,
чтобы убрать раздачу результата по панелям вручную, но сам «текущий
результат» по-прежнему живёт атрибутом `MainWindow._current_result` и
присваивается в трёх местах (`ui/main_window.py`, строки ~1133, ~1325,
~1743). Любой новый путь, забывший строчку, молча ломает
Clean/Article/Insights/YouTube/Book — они проверяют `if not
self._current_result` и тихо выходят с «нет транскрипции».

**Решение.** Владельцем становится сессия.

*Где:* `application/document_session.py`, `ui/main_window.py`.

1. В `DocumentSession`: приватное поле `_result: TranscriptionResult |
   None = None`; `apply_result()` сначала пишет его, потом делает
   раздачу; добавить свойство `current_result` и метод `clear()`.
2. В `MainWindow` удалить атрибут `_current_result` целиком. Добавить
   read-only свойство:
   ```python
   @property
   def current_result(self) -> TranscriptionResult | None:
       return self._document_session.current_result
   ```
   и заменить все чтения. Присваиваний не остаётся ни одного — попытка
   присвоить упадёт с `AttributeError`, потому что свойство без сеттера.
3. Проверить порядок на каждом из трёх бывших мест: сейчас где-то
   `_current_result` ставится **до** `apply_result()`, где-то после;
   после переноса порядок задаёт сама сессия.

**Критерии приёмки.**
- В `ui/main_window.py` нет ни одного присваивания `_current_result`.
- Панели Clean/Article/Insights/YouTube/Book работают после свежей
  расшифровки, после открытия из библиотеки и после ручной правки
  транскрипта (три пути, которые раньше присваивали отдельно).

**Тесты.** Новый `tests/test_main_window_result_ownership.py` в стиле
уже существующего слоевого сторожа `tests/test_domain_transcription.py`:
разобрать `ui/main_window.py` через `ast`, обойти дерево и упасть на
любом `Assign`/`AugAssign`, чей target — `self._current_result` или
`self.current_result`. Плюс Qt-тест: `apply_result()` → `window
.current_result is result`.

**Риск.** Свойство без сеттера — намеренно ломающее изменение: если
где-то в `ui/` осталось присваивание, оно упадёт в рантайме, а не молча.
Поэтому AST-сторож должен быть в том же коммите.

## A2. Два чипа «Все» подряд — `S`

**Проблема.** В библиотеке два независимых ряда фильтров (источник и
рецепт), у каждого свой чип «Все», без подписей — визуально
неразличимы. Видно на любом скриншоте библиотеки.

**Решение.** Подписать ряды и дать сброс.

*Где:* `ui/library_view.py::_setup_ui`, `locales/{en,ru}.json`.

1. Перед каждым `FlowLayout` добавить приглушённый `QLabel` с
   `setProperty("role", "muted")` — как это уже сделано на старт-экране
   (`ui/start_view.py`, метка «Рецепт»). Новые ключи локали:
   `library_filter_source_label` («Источник» / «Source»),
   `library_filter_recipe_label` («Рецепт» / «Recipe»).
2. Добавить ghost-кнопку «Сбросить» (`library_filters_reset`), видимую
   только когда активен хотя бы один нестандартный фильтр или непустой
   поиск. По клику: `_set_filter("all")`, `_set_recipe_filter("all")`,
   очистить поле поиска.

**Критерии приёмки.** Обе метки видны; кнопка сброса скрыта на холодном
старте, появляется после любого фильтра и возвращает список к полному.

**Тесты.** Расширить `tests_qt/test_library_view.py`: видимость меток;
цикл «поставить фильтр → кнопка появилась → нажать → оба
`QButtonGroup` снова на «Все» и поле поиска пустое».

## A4. «Настроить…» всегда перезаписывает слот — `S`

**Проблема.** `MainWindow._open_recipe_editor()` при любом «Сохранить»
пишет `cfg.recipes = [custom.to_dict()]` и переключает `last_recipe` на
`"custom"` — даже если пользователь ничего не менял. Встроенный рецепт,
с которого начинали, теряется молча, и все чипы гаснут.

**Решение.** Сохранять только реальное изменение и называть результат.

*Где:* `ui/main_window.py::_open_recipe_editor`, `ui/recipe_editor.py`.

1. В `_open_recipe_editor` запомнить исходный ключ и рецепт. После
   `accept`: если `tuple(steps) == tuple(original.steps)` — не трогать
   `cfg.recipes` вообще, вызвать `start_view.set_recipe(original_key)` и
   `refresh_summary()`, выйти.
2. В `RecipeEditorDialog` добавить `QLineEdit` с именем. Значение по
   умолчанию при открытии на встроенном рецепте —
   `tr("recipe_editor_default_name", base=tr(f"recipe_{key}"))`
   («{base} (изменённый)»). Метод `recipe_name() -> str`.
3. Под полем — приглушённая подсказка `recipe_editor_saves_as_copy`:
   «Изменения сохранятся как отдельный рецепт, встроенный останется как
   есть».
4. Сохранять `Recipe(name=dialog.recipe_name(), steps=steps,
   builtin_key="")` — добавлением в список, а не заменой (это уже часть
   B4; до B4 — заменой, но с именем).

**Критерии приёмки.** Открыть редактор на «Статья из подкаста», нажать
«Сохранить» ничего не меняя → `Config.recipes` не изменился,
`last_recipe == "podcast_article"`, чип остался отмеченным. Снять шаг →
сохраняется новый рецепт под введённым именем.

**Тесты.** `tests_qt/test_ui_audit_regressions.py` — оба сценария.

## A5. Мастерская обложек достижима из одного места — `S`

**Проблема.** Единственный вход — кнопка «Обложки» в панели библиотеки.
Её нет ни в меню-баре, ни в палитре Ctrl+K, ни на экране записи, хотя
обложка делается **для записи**.

**Решение.** Три входа плюс правильный контекст.

*Где:* `ui/command_palette.py`, `ui/main_window.py`, `ui/record_view.py`.

1. Палитра: добавить `("cover", "command_cover")` в `_ACTIONS`; в
   `MainWindow._run_palette_action` — `"cover": lambda:
   self._on_section_changed("cover")`. *(После B12 этот шаг исчезнет
   сам: палитра будет строиться из меню-бара.)*
2. Меню-бар: в «Переход» пункт «Обложки» с `Ctrl+4` (свободен; 1–3
   заняты).
3. `RecordView`: кнопка «Обложка» в шапке рядом с «Очистить текст» /
   «Создать статьи», сигнал `cover_requested`. `MainWindow` открывает
   мастерскую — данные записи там уже есть, `cover_view.set_segments()`
   вызывается через `DocumentSession`.
4. Кнопку в панели библиотеки превратить в иконочную (`get_icon('image',
   …)`, `setFixedWidth(28)`) — она перестала быть единственным входом,
   и это освобождает строку панели.

**Критерии приёмки.** Мастерская открывается из палитры, из меню и с
экрана записи; из последнего — с уже загруженными сегментами открытой
записи.

**Тесты.** `tests_qt/test_command_palette.py` — строка «Обложки» есть и
переключает `_stack` на `_cover_index`. `tests_qt` для кнопки на
`RecordView`.

## A6. Очередь папки не применяет рецепт — `M`

**Проблема.** `MainWindow._on_batch_item_finished()` только сохраняет в
историю. При этом на старт-экране при выбранном источнике «Папка» виден
пикер рецептов — интерфейс обещает то, чего не делает.

**Решение (полное).** Прогонять рецепт для каждого файла очереди,
последовательно.

*Где:* `ui/main_window.py`.

1. **Развязать `_run_recipe` от состояния окна.** Сейчас он читает
   `self._source_filepath` и `self._last_record_id`. Сменить сигнатуру
   на
   ```python
   def _run_recipe(self, result, *, source_path: str, record_id, show_run_screen: bool = True) -> None
   ```
   и обновить существующего вызывающего (`_on_finished`, строка ~1420).
   Это самостоятельный рефакторинг — отдельным коммитом до всего
   остального.
2. **Очередь прогонов.** `self._recipe_job` — один слот, а батч
   заканчивает файлы подряд. Завести
   `self._pending_recipe_runs: deque[tuple]`; `_on_batch_item_finished`
   кладёт в неё `(result, source_path, record_id)` и запускает
   немедленно, только если `self._recipe_job is None`.
   `_on_recipe_job_finished` в конце достаёт следующий из очереди.
3. **Важно про сериализацию.** `JobEngine(resource_limits)` создаётся на
   каждый `JobRunner`, то есть лимит `local_llm=1` действует **внутри
   одного прогона**, а не между прогонами. От параллельных запросов к LM
   Studio спасает только `_serialized_completion` в
   `core/lm_client.py` (на уровне вызова). Очередь из шага 2 — не
   украшение, а условие предсказуемого поведения; полагаться на лимиты
   движка здесь нельзя.
4. Прогоны батча запускать с `show_run_screen=False` (как уже делает
   live-путь), чтобы не выдёргивать пользователя из того, что он
   смотрит; итог виден по бейджам в библиотеке.

**Решение (минимальное, если полное откладывается).** В
`StartView.set_source` скрывать ряд рецептов и метку для источника
`"folder"`, а в описание папки добавить строку «в очереди выполняется
только расшифровка». Интерфейс перестанет обещать лишнее — 10 минут
работы вместо `M`.

**Критерии приёмки (полное).** Два файла в очереди с рецептом «Статья из
подкаста» → оба прогона выполняются по очереди (никогда одновременно),
у обеих записей в библиотеке появляются бейджи материалов.

**Тесты.** `tests_qt` с двумя фиктивными элементами очереди и
runner-ами-заглушками: утверждать, что второй прогон стартует не раньше
`job_finished` первого.

## A7. `StatusBar.setVisible()` игнорирует аргумент — `S`

**Проблема.** Переопределение зовёт `super().setVisible(True)` независимо
от аргумента, то есть `hide()` молча не работает. Это шим под снятые
вызовы, но нарушенный контракт `QWidget` — ровно тот класс проблем, что
и `self.layout` в `ui/components.py` (уже исправлено).

**Решение.** Починить вызывающих, убрать ложь.

*Где:* `ui/status_bar.py`, `ui/main_window.py`.

1. В `StatusBar` добавить
   ```python
   def set_busy(self, busy: bool) -> None:
       """Показать/скрыть индикаторы операции, не трогая саму панель."""
   ```
   — показывает/прячет `progress` и `cancel_button`. Переопределение
   `setVisible` удалить.
2. В `MainWindow` заменить шесть мест с `self.operation_bar`:
   `setVisible(True)` (строка ~1199) и `setVisible(run_active)`
   (~1852) → `self.status_bar.set_busy(...)`; `set_operation`/`clear`
   оставить как есть, но звать через `self.status_bar`.
3. Удалить алиас `self.operation_bar = self.status_bar` (строка ~689) —
   он остался от снятого `OperationBar`.

**Критерии приёмки.** `status_bar.setVisible(False)` реально скрывает
панель; `set_busy(False)` оставляет панель на месте, убирая прогресс и
Cancel.

**Тесты.** `tests_qt/test_window_chrome_regressions.py` — оба
утверждения.

## A9. Пять мелочей — `S` каждая

**a) Вкладки записи мешают эмодзи и не-эмодзи.**
«📝 Транскрипт», «✨ Очищенный», «YouTube», «💬 Чат». Эмодзи не
локализуются, ломают выравнивание и уже несогласованны.
*Решение:* убрать эмодзи из всех ключей `tab_*` в `locales/{en,ru}.json`.
*Тест:* в `tests/` — все значения ключей `tab_*` состоят только из
`str.isprintable()` символов без пиктограмм (диапазоны U+1F300–U+1FAFF,
U+2190–U+27BF).

**b) Меню экспорта закрывается на каждом переключении формата.**
Выбрать три формата = открыть меню три раза.
*Решение:* класс `KeepOpenMenu(QMenu)` в `ui/components.py`,
переопределяющий `mouseReleaseEvent`: если под курсором checkable-action —
переключить его и **не** звать `super()`. Использовать в
`RecordView._build_export_menu`.
*Тест:* Qt — после `mouseReleaseEvent` по checkable-пункту меню всё ещё
`isVisible()`, а по «Экспортировать» — закрывается.

**c) Меню экспорта читает `Config.export_formats` один раз.**
После смены форматов в настройках галочки устаревают.
*Решение:* `RecordView.refresh_export_formats()` — перечитывает конфиг и
переставляет `setChecked` у `self._format_actions`. Звать из
`MainWindow._on_settings_applied`.
*Тест:* Qt — сменить `cfg.export_formats`, вызвать
`_on_settings_applied`, проверить галочки.

**d) `set_operation(cancel_text=…)` не восстанавливает подпись.**
Кастомная подпись («Остановить запись») прилипает к следующей операции.
*Решение:* в `ui/status_bar.py` всегда
`self.cancel_button.setText(cancel_text or tr("btn_cancel"))`.
*Тест:* unit-стиля Qt-тест на две последовательные `set_operation`.

**e) `_QueueOverlay.show_above()` не ограничен экраном.**
`self.move(pos.x(), pos.y() - self.height() - 6)` может увести окно 420×460
за край.
*Решение:* зажать в `QGuiApplication.screenAt(pos).availableGeometry()`
(с `primaryScreen()` как запасным), по обеим осям.
*Тест:* Qt — подвинуть окно к правому/нижнему краю, проверить, что
геометрия оверлея внутри `availableGeometry()`.

```python
self._recipe_job.set_runners(
    runners, cache_checks=build_cache_checks(self._recipe_context, self._recipe_step_names)
)
```

**(2) Регидратация — это и есть настоящая работа.** При попадании в кэш
шаг получает `StepStatus.SKIPPED` и `outcome.result is None`. Отсюда две
поломки, которые надо закрыть в том же коммите:

- `MainWindow._on_recipe_step_finished` наполняет панели только на
  `SUCCEEDED` — пропущенный шаг оставит вкладку пустой, хотя файл
  материала лежит на диске;
- `StepContext.get_result(name)` отдаёт `run.outcomes[name].result`, то
  есть `None` — и зависимый шаг (`article` читает `clean`) сломается.

*Решение.* Дать реестру шагов обратную операцию к записи:

1. В `StepDefinition` добавить поле
   `load_artifact: Callable[[StepContext], Optional[Any]]` — читает файл,
   который `make_artifact()` описывает, и восстанавливает объект того же
   типа, что вернул бы runner. Для `clean` это `ProcessingResult`, для
   `article` — `GenerationResult`, для `insights`/`youtube_package` —
   `dict`, для `book` — `BookResult`, для `cover` — путь к PNG.
   Шаги, у которых `make_artifact()` возвращает `None`
   (`transcribe`/`diarize`), получают загрузчик `lambda ctx: None`.
2. `_run_recipe` строит `get_result` так, чтобы при `result is None` и
   статусе `SKIPPED` он звал `STEP_REGISTRY[name].load_artifact(context)`
   и кэшировал результат в словаре на время прогона.
3. `_on_recipe_step_finished`: ветку наполнения панелей выполнять и для
   `SKIPPED`, беря значение через тот же загрузчик.

**(3) Принудительная перегенерация.** Иначе пользователь, которому просто
нужен другой вариант при тех же входных данных, окажется заперт в кэше.
`transcript_revision` меняется при правке транскрипта, `source_hash` —
при замене файла, `prompt_version` — при правке промпта, так что кэш
инвалидируется сам в трёх случаях из четырёх; четвёртый — «хочу другой
вариант» — нужно закрыть кнопкой.
*Решение:* в `RunView` у строки шага, помимо «Повторить», пункт
«Сгенерировать заново» (контекстное меню строки), который перед
`retry_requested` удаляет манифест (`artifact_store.manifest_path_for()`)
— cache-check тогда честно вернёт `False`.

**Критерии приёмки.**
- Прогнать «Статья из подкаста» дважды на одной записи: во втором
  прогоне `clean` и `article` → `SKIPPED`, вкладки «Очищенный» и
  «Статьи» заполнены, суммарное время < 10% первого.
- Править транскрипт → следующий прогон снова выполняет шаги (revision
  изменился).
- «Сгенерировать заново» на пропущенном шаге реально запускает его.

**Тесты.**
- `tests/test_steps.py`: для каждого шага с непустым `make_artifact()` —
  round-trip «runner записал → `load_artifact` прочитал → объект
  эквивалентен».
- `tests_qt/test_recipe_retry.py`: два прогона подряд, утверждать
  `SKIPPED` и непустые панели.
- `tests_qt`: удаление манифеста снимает пропуск.

**Риски.** `insights` кладёт результаты в общий `insights_cache` в
памяти — проверить, что дисковый кэш и он не расходятся. Формат
сериализации материалов сейчас задан теми же runner-ами; если какой-то
пишет не всё, что нужно для восстановления объекта, `load_artifact`
придётся дописать вместе с записью — это допустимо, но должно быть
отдельным коммитом на шаг.

## B2. Возобновление прерванного прогона — `M` *(нужен B1)*

**Состояние.** `application/run_store.py` уже пишет и читает исходы
шагов в `job_runs` (схема v4), включая `load_run`, `load_latest_runs` и
`apply_stored_outcomes`. Библиотека читает оттуда только «какие шаги
упали» для бейджей — самих прогонов возобновить нельзя.

**Что сделать.**

1. `application/run_store.py`: `mark_stale_running_as_interrupted()` —
   переводит в `interrupted` все строки со `status='running'` при старте
   приложения (процесс, который их писал, уже мёртв — иначе они были бы
   в памяти). Вызвать один раз из `MainWindow.__init__`.
2. Карточка записи в библиотеке (`RecordItemWidget`): если у последнего
   прогона статус `failed`/`interrupted` и есть шаги без `SUCCEEDED`,
   показать кнопку «Продолжить». Сигнал `resume_run(record_id)`.
3. `MainWindow._resume_run(record_id)`:
   - `_load_from_history(record_id)` (восстановит транскрипт и панели);
   - `run = run_store.load_run(run_id)`; собрать `JobSpec` из
     `build_job_spec(run.recipe, steps_of(run.recipe))`;
   - `JobRun(spec=spec)` + `apply_stored_outcomes(run)`;
   - `run_view.bind_run(...)`, `set_recipe_name(...)`,
     `set_finished(False)`, переключиться на экран прогона,
     `_launch_recipe_job()`.
4. **Зависимость от B1.** У восстановленных исходов `result is None` по
   контракту `run_store` — зависимые шаги смогут работать только через
   `load_artifact`. Без B1 возобновление будет падать на первом же шаге,
   которому нужен вывод предшественника.

**Критерии приёмки.** Запустить рецепт из 4 шагов, убить процесс после
второго, запустить приложение заново → карточка показывает «Продолжить»,
нажатие доигрывает оставшиеся два, первые два помечены как выполненные.

**Тесты.** `tests_qt/test_recipe_run_persistence.py`: записать прогон с
частичными исходами прямо в стор, вызвать `_resume_run`, утверждать что
выполнились только недостающие шаги.

**Риск.** Рецепт мог измениться между запусками (B4 делает это
вероятным). Если состав шагов сохранённого прогона не совпадает с
текущим рецептом — возобновлять по **сохранённому** составу, а не по
текущему, и показать это в заголовке экрана прогона.

   CREATE TABLE IF NOT EXISTS speaker_aliases (
       alias       TEXT PRIMARY KEY,
       used_count  INTEGER NOT NULL DEFAULT 1,
       updated_at  TEXT    NOT NULL
   );

2. `HistoryStore.remember_speaker_alias(alias)` (upsert + инкремент) и

это имя первое в списке подсказок. Подсказка не подставляется сама.

**Тесты.** Юнит на порядок `list_speaker_aliases` и на идемпотентность
upsert; Qt-тест на предзаполнение комбобокса.

## B7. Поиск по сгенерированным материалам — `L`

**Проблема.** FTS5 индексирует только `transcripts(source_name,
json_payload)`. Статьи, инсайты, YouTube-пакеты, книга не ищутся вообще —
а именно их и хочется искать через полгода («где я говорил про
ценообразование» найдётся, «где была статья про ценообразование» — нет).

**Что сделать.**

1. Миграция `_v6_add_artifact_texts` :
   ```sql
   CREATE TABLE IF NOT EXISTS artifact_texts (
       id         INTEGER PRIMARY KEY AUTOINCREMENT,
       record_id  INTEGER NOT NULL,
       type       TEXT    NOT NULL,
       path       TEXT    NOT NULL,
       text       TEXT    NOT NULL,
       updated_at TEXT    NOT NULL,
       UNIQUE(record_id, type)
   );
   CREATE INDEX IF NOT EXISTS idx_artifact_texts_record ON artifact_texts(record_id);
   ```
   плюс FTS5-зеркало по образцу `_CREATE_FTS_SQL` — с теми же триггерами
   и той же аккуратной обработкой отсутствия FTS5
   (`_fts_available`, `fts_state`, `repair_fts` уже написаны, надо
   обобщить их на два индекса, а не копировать).
2. Индексация — в `application/steps.py::_save_artifact`: помимо
   манифеста, извлечь из результата плоский текст и записать в
   `artifact_texts`. Для каждого типа своя функция извлечения
   (у `insights` это заголовки глав и пункты, у `article` — тела статей).
   Ошибка индексации не должна валить успешный шаг — та же best-effort
   поза, что уже принята для манифеста.
3. `HistoryStore.search_artifacts(query, limit)` → строки с `record_id`,
   `type`, сниппетом.
4. UI: у поля поиска в библиотеке переключатель области
   («Транскрипты / Материалы / Всё»). Результат-материал открывает
   запись **на нужной вкладке** — для этого `open_record` должен нести
   ещё и тип, а `MainWindow._open_record_view` — уметь выбрать вкладку
   по типу артефакта (маппинг, обратный `_STEP_TO_ARTIFACT_TYPE`).
5. Палитра Ctrl+K ищет по обеим областям.
6. Обратное заполнение: для существующих записей материалы лежат на
   диске с манифестами. Разовая процедура `reindex_artifacts()` в
   настройках («Переиндексировать материалы»), а не автоматически при
   старте — это может быть долго.

**Критерии приёмки.** Сгенерировать статью со словом-маркером, найти её
поиском в области «Материалы», клик открывает запись на вкладке
«Статьи».

**Тесты.** Юниты на извлечение текста по каждому типу; юнит на
`search_artifacts`; Qt-тест на переключатель области и открытие нужной
вкладки.

**Риск.** Размер БД. Тексты материалов на порядок меньше аудио, но для
книги это мегабайты — ограничить индексируемый текст (например, 200 КБ

   расшифровано»).
4. UI: кнопка «Версии» в шапке `RecordView` → немодальный диалог со
   списком (дата, число слов, размер изменения). Выбрать две → unified
   diff через `difflib.unified_diff` по строкам сегментов, с подсветкой.
   Кнопка «Восстановить» применяет версию через
   `DocumentSession.apply_result()` (то есть по всем панелям сразу — как
   раз то, ради чего A1 приводит владение результатом в порядок).
5. Связка с B1: восстановление старой версии меняет
   `transcript_revision`, и кэш материалов честно инвалидируется —
   отдельной работы не требует, но это стоит проверить тестом.

**Критерии приёмки.** Правка → через 5 с в списке новая версия;
восстановление возвращает текст и обновляет все вкладки; следующий
прогон рецепта не пропускает шаги по кэшу.

**Тесты.** Юниты на запись/прунинг/дебанс-логику (чистую часть вынести из
Qt); Qt-тест на восстановление и на инвалидацию кэша после него.

**Риск.** `json_payload` версии — это полный транскрипт. При 20 версиях
часового разговора это десятки мегабайт на запись. Если это окажется
много — хранить diff'ы, а не полные копии; но начинать стоит с простого
варианта и ограничения `transcript_revisions_kept`.

## B9. Экспорт-пресеты — `M`

**Проблема.** «Собрать YouTube-пакет» = вручную отметить форматы,
выгрузить, потом руками собрать описание, тайм-коды, теги и обложку из
разных мест.

**Что сделать.**

1. `domain/export_preset.py` (Qt-free):
   ```python
   @dataclass(frozen=True)
   class ExportPreset:
       key: str            # ключ локали: preset_<key>
       formats: tuple[str, ...]    # ключи exporters.EXPORT_FORMATS
       artifacts: tuple[str, ...]  # типы Artifact
   ```
   Встроенные: `youtube` (srt + vtt + youtube-пакет + обложка),

   материалы).

   directory, record_id)` — переиспользует `export_many_to_directory`

   Отсутствующий материал — пропуск со строкой в отчёте, а не ошибка

   генерировали).
3. `RecordView`: пресеты первым блоком меню экспорта, форматы — ниже,

**Критерии приёмки.** На записи с YouTube-пакетом и обложкой пресет
кладёт в папку ожидаемый набор и `index.txt`; на записи без них —
кладёт что есть и честно сообщает про пропущенное.

**Тесты.** `tests/test_export_controller.py` — оба сценария на `tmp_path`,
без Qt (контроллер Qt-free по построению).

## B10. Бейдж скачанной модели — `S`

**Проблема.** В комбобоксе модели можно выбрать нескачанные веса и
узнать об этом только при запуске транскрипции.

**Что есть.** `core/model_repository.py::ModelRepository.validate(key)`
уже проверяет наличие и целостность; `core/model_manifest.py::ModelEntry`
знает размер.

**Что сделать.**

1. `ui/option_labels.py`: `whisper_model_options_with_state() ->
   list[tuple[str, str, bool]]` — `(key, label, downloaded)`.
   Существующую `whisper_model_options()` не трогать: её использует
   `ui/live_setup_panel.py`.
2. `ui/transcribe_options.py::_fill_combo` для модели: к тексту
   добавлять суффикс — `«· скачана»` / `«· ~547 МБ, будет загружена»`.
   Именно текстом, не только цветом (правило проекта: цвет никогда не
   единственный сигнал). Полный текст — в tooltip.
3. Состояние считать **один раз** при построении и обновлять по событию:
   после `_on_settings_applied` и после успешной загрузки модели
   (`ui/model_downloader.py` уже сигналит о завершении) — но никогда не
   в `paintEvent` и не на каждое открытие списка: `validate()` считает
   sha256 и это дорого.
   Если `validate()` окажется слишком медленным даже разово — достаточно
   проверки существования файла нужного размера, а полную валидацию
   оставить моменту запуска.
4. То же в `ui/live_setup_panel.py::model_combo` — там та же проблема.

**Критерии приёмки.** Скачанные модели помечены в списке; после загрузки
новой пометка появляется без перезапуска; открытие списка не тормозит.

**Тесты.** Юнит на `whisper_model_options_with_state()` с подставным
каталогом моделей; Qt-тест на суффикс в тексте элемента.

## B12. Палитра строится из меню-бара — `M`

**Проблема.** В палитре Ctrl+K шесть захардкоженных действий
(`ui/command_palette.py::_ACTIONS` + словарь обработчиков
`MainWindow._run_palette_action`), в меню-баре — около двадцати. Два
списка расходятся при каждом изменении, и палитра не знает, доступно ли
действие сейчас.

**Что сделать.**

1. `MainWindow._init_menu_bar` сейчас создаёт `QAction` подряд.
   Переписать декларативно: список кортежей
   `(menu_key, action_key, shortcut, slot, in_palette: bool)`, из
   которого строится и меню-бар, и список для палитры. Метод возвращает
   `list[QAction]`, помеченных для палитры.
2. `CommandPalette`: заменить `_ACTIONS` на `bind_actions(actions:
   list[QAction])`. В `_refresh` рисовать `action.text()` (то есть ровно
   ту же подпись, что в меню) и фильтровать по ней. В `_activate` —
   `action.trigger()` вместо испускания строкового ключа.
3. Удалить `MainWindow._run_palette_action` целиком и сигнал
   `action_requested` — они становятся лишним слоем.
4. Недоступные действия (`action.isEnabled() is False`) либо не
   показывать, либо показывать неактивными — выбрать одно и
   зафиксировать тестом. Рекомендация: **показывать неактивными**, чтобы
   пользователь понимал, что функция есть, но сейчас неприменима.
5. Строки рецептов, шагов для перезапуска и записей остаются как есть —
   они не действия меню.

**Критерии приёмки.** Каждый помеченный пункт меню-бара присутствует в
палитре с той же подписью; активация строки палитры делает ровно то же,
что пункт меню; добавление нового пункта меню автоматически появляется в
палитре без правки `command_palette.py`.

**Тесты.** `tests_qt/test_command_palette.py`: собрать все `QAction` окна
с флагом палитры и утверждать, что каждый нашёлся в списке; подменить
`trigger` у одного и проверить, что активация строки его вызвала.

**Побочная выгода.** Это же снимает шаг 1 из A5 — «Обложки» попадут в
палитру автоматически, как только появятся в меню.
