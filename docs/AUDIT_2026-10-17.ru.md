## 1. Вывод

Проект имеет рабочую среду разработки, выделенные слои, значительный набор тестов и несколько полезных защит: проверку моделей по SHA-256, атомарное сохранение конфигурации и манифестов, PKCE для OAuth, реестр фоновых Qt-воркеров. Повторный запуск **1 702 существующих тестов прошёл**.

Однако зелёные проверки не подтверждают корректность нескольких важных пользовательских сценариев. Обнаружены **14 замечаний: 6 уровня P1 и 8 уровня P2**. Двенадцать замечаний о поведении приложения проверены отдельными воспроизведениями; ещё два подтверждены проверкой зависимостей и запуском закреплённого mypy.

Основные проблемы сосредоточены в контрактах между компонентами:

- настройки облачного провайдера YouTube попадают в рецепт заметок встречи;
- состояние завершённого шага, фактический успех операции и пригодность кэша могут противоречить друг другу;
- возобновление рецепта и возобновление загрузки видео не полностью учитывают актуальные намерения пользователя;
- ключи версий и кэшей описывают лишь часть входных данных.

До устранения P1 не следует считать проверенными конфиденциальность всех рецептов, восстановление после ошибки, надёжную отмену генерации и корректность продолжения YouTube-загрузки после изменения пакета.

Это не заключение о компрометации пользователей: реальные записи, ключи и аккаунты в проверках не использовались, внешние AI API и YouTube API не вызывались.

### A01. Облачный провайдер выходит за границу функции YouTube

**Код:** `ui/recipe_run_controller.py:90–120`, `application/steps.py:522–545`, `application/steps.py:1111–1134`, `core/insights.py:342–365`.

`RecipeRunController._build_context()` передаёт `provider_from_config(cfg)` в общий контекст рецепта. `_insights_runner()` извлекает этот `provider` и передаёт его для `chapters`, `action_items`, `key_moments`. `generate_insight()` без проверки области применения создаёт соответствующий облачный клиент.

**Сценарий:** пользователь настроил OpenAI для YouTube, затем запускает рецепт «Meeting notes». В README и `core/ai_provider.py` заявлено, что другие AI-функции используют LM Studio. На этом пути текст встречи и её заметки могут уйти облачному провайдеру.

**Доказательство:** изолированный запуск Insights с параметрами, собранными тем же `llm_params()`, выбрал `openai` **три раза**. Реального запроса и утечки пользовательских данных при аудите не было.

**Исправление:** разделить настройки провайдера по функциям; в Insights не принимать YouTube-provider. Если облачные Insights нужны продукту, добавить отдельное явное согласие и соответствующее описание. Нельзя ограничиться изменением README, сохранив неожиданную отправку.

**Регрессия:** при `Config(yt_provider='openai')` рецепт встречи обязан создавать только локальный клиент; отдельный YouTube-рецепт должен продолжать использовать выбранный облачный.

### A02. Возобновление не повторяет ошибочные шаги

**Код:** `ui/recipe_run_controller.py:168–226`, `application/run_store.py:240–259`, `application/job_engine.py:127–181`.

`resume()` восстанавливает все outcomes, включая `FAILED` и `CANCELLED`, и вызывает `_launch()`. Engine выбирает только шаги, которых вообще нет в `run.outcomes`. Сброс неуспешных outcomes перед запуском отсутствует. Ручная кнопка retry имеет другой путь и не устраняет дефект кнопки «Продолжить».

**Доказательство:** сохранённый run с успешной транскрипцией и ошибочной очисткой прошёл через настоящий `resume()` с подставным UI. Вызовов runner — **0**, состояние очистки осталось `failed`.

**Последствие:** восстановление после недоступного LLM, отмены или ошибки возвращает пользователя в тот же ошибочный run без выполнения работы. После crash могут продолжиться только шаги, не успевшие получить outcome.

**Исправление:** сохранять только пригодные успешные результаты; сбрасывать FAILED/CANCELLED и зависимые исходы, проверять наличие и актуальность артефактов успешных шагов. Делать это в общей функции восстановления, а не только в обработчике UI.

**Регрессия:** сохранить run `transcribe=SUCCEEDED, clean=FAILED, article=CANCELLED`, восстановить и проверить реальное выполнение clean/article без повторной транскрипции.

### A03. Неуспешный BookResult становится успешным кэшем

**Код:** `book_pipeline.py:192–345`, `application/steps.py:678–710`, `application/job_engine.py:207–219`.

`BookPipeline.process()` возвращает `BookResult` с `success=False` при пустом ответе LLM, недоступном custom prompt или ошибке записи стадии. `_book_runner()` не проверяет `result.success`: пишет `result.final_text`, сохраняет манифест и возвращает объект. Engine считает любое не выбросившее исключение выполнение успешным.

**Доказательство:** для `BookResult` с неуспешной стадией получены `pipeline_success=false`, `job_status=succeeded`, размер `book.md` **0 байт**, `cache_valid=true`.

**Последствие:** пользователь получает ложное завершение, пустой файл может заменить предыдущую книгу, последующие запуски могут пропускать работу по кэшу. Если ошибка случилась после успешной первой стадии, частичный результат также маскируется как полная книга.

**Исправление:** до записи общего результата проверять контракт успеха и завершённость выбранных стадий; передавать ошибку в engine. Хранить частичные стадии отдельно, не маркируя их полной книгой.

**Регрессия:** no-response, ошибка чтения prompt и ошибка второй стадии должны давать FAILED, не изменять предыдущий успешный `book.md` и не создавать пригодный манифест полной книги.

### A04. Хэш версии не описывает все значимые изменения транскрипта

**Код:** `domain/artifact_provenance.py:40–60`, `core/insights.py:192–220`, `core/history.py:1018–1042`, `ui/main_window.py:1874–1895`.

`transcript_revision()` хэширует текст сегментов и язык, пропуская start/end и speaker. При этом prompt Insights включает таймкоды и speaker. Одинаковый текст с новым временем/спикером имеет другой фактический запрос, но тот же дисковый cache key.

Для истории проблема распространяется на переименование: `save_current_revision()` по умолчанию использует текстовый хэш, а `speaker_names` не включает даже в режим `include_speakers=True`. Обычный debounced save вызывается без этого флага.

**Доказательство:** смена начала сегмента `0 → 120` секунд и speaker `S1 → S2` изменила prompt, но не ключ Insights. Последовательное сохранение той же транскрипции с именами Alice и Bob **не создало вторую версию**.

**Последствие:** старые главы и атрибуция сохраняются после изменения разметки; переименование спикеров не получает ожидаемой отдельной восстанавливаемой версии.

**Исправление:** определить отдельные канонические ревизии для полного документа и текстовых задач. В документ включить сегменты, времена, speaker IDs и отображаемые имена; для генераторов хэшировать ровно те данные, которые входят в запрос. Версионировать формат ключа для безопасного сброса старого кэша.

**Регрессия:** независимые изменения текста, таймингов, speaker ID и speaker name; проверить новый ключ в нужных задачах и новую запись версии.

### A05. Параметры генерации и модель не полностью входят в идентичность кэша

**Код:** `application/steps.py:384–395`, `application/steps.py:466–477`, `application/steps.py:713–724`, `core/insights.py:342–351`, `core/insights_cache.py:41–47`.

Дисковый ключ книги учитывает только стандартный prompt «расшивка», но не `do_unwrap`, `do_custom`, путь/содержимое custom prompt и фактические параметры книжного клиента. In-memory InsightsCache использует `provider.kind`, prompt и тип задачи, не учитывая модель и endpoint. Смена OpenAI-compatible сервера или модели внутри одного provider kind может вернуть ответ предыдущей модели.

Аналогичная неполнота видна у `use_ai` очистки и списка `article_formats`; отдельно эти два случая динамически не воспроизводились. Они требуют проверки при исправлении общей схемы ключей.

**Доказательство:** включение custom-стадии книги и изменение содержимого её prompt сохранили прежний ключ. Два запроса Insights к `model-A` и `model-B` с общим кэшем вызвали фактическую генерацию **только у model-A**.

**Исправление:** хэшировать нормализованный набор результатообразующих параметров: backend/endpoint, модель, язык, выбранные стадии/форматы, prompt contents и upstream-артефакты. Не включать API key в ключ или манифест. Использовать фактический provider каждого шага, а не общий YouTube-provider.

**Регрессия:** матрица изменений по одному параметру; неизменные входы должны давать hit, изменяющие результат — miss.

### A06. Перегенерация шага не инвалидирует успешных потомков

**Код:** `application/job_engine.py:92–107`, `ui/recipe_run_controller.py:337–356`, `application/steps.py:434–440`.

`reset_step()` рекурсивно удаляет только зависимые outcomes со статусом CANCELLED. Успешная статья остаётся успешной после сброса и новой генерации очистки, хотя article runner использует результат clean. `regenerate()` удаляет манифест только выбранного шага.

**Доказательство:** после `reset_step('clean')` и повторного запуска clean стал `new clean`, article остался `old article`; runner статьи **не вызывался**.

**Последствие:** один run одновременно показывает результаты от разных поколений входных данных. Повторный полный запуск также должен учитывать upstream-ревизию в дисковом кэше, иначе сброс outcomes сам по себе недостаточен.

**Исправление:** вычислять транзитивных потомков и явно помечать/сбрасывать их при изменении выхода предшественника. В ключ артефакта потомка включать fingerprint фактически использованного upstream-результата. Нужную пользователю возможность сохранить старые производные результаты оформить отдельным действием.

**Регрессия:** DAG `clean → article`, перегенерация clean с новым текстом, затем проверка исполнения article и нового provenance.

### A07. Resumable upload продолжает старую сессию с новыми локальными метаданными

**Код:** `core/youtube_upload.py:125–145`, `core/youtube_upload.py:217–274`, `core/youtube_upload.py:322–348`.

Pending-файл хранит fingerprint видео, URI и title; `load_pending()` проверяет только путь, размер и целочисленный mtime файла. Даже сохранённый title не сравнивается. Title/description/tags/privacy/made_for_kids передаются YouTube только при создании сессии.

**Сценарий:** загрузка началась с `unlisted`, прервалась; пользователь изменил пакет на `private` или исправил описание и продолжил. Клиент использует прежнюю сессию, затем записывает локальный `UploadRecord` из нового пакета.

**Доказательство:** смоделирован завершённый ответ сохранённой сессии с прежним title и `unlisted`. Новая сессия не создавалась, запрос обновления не выполнялся, локальная запись получила **новый title и `private`**. Настоящая интеграция с Google не проверялась; подтверждён выбор протокольного пути и несоответствие локального учёта.

**Последствие:** пользователь может считать видео приватным, когда сессия создавалась для unlisted. Unlisted не означает общедоступный поиск, но разрешает просмотр по ссылке. Метаданные и локальная история могут расходиться с сервером.

**Исправление:** связывать pending session с полным хэшем подтверждённого пакета, включая privacy и fingerprint содержимого/точный mtime. При расхождении предложить явный выбор перезапуска или обновления. После завершения сверять фактический серверный результат до записи локального статуса.

**Регрессия:** изменить только privacy/title после interruption, не меняя видео; запросы и сохранённый record должны соответствовать новой подтверждённой политике.

### A08. CLI конфигурации выводит OAuth client secret без маскирования

**Код:** `config.py:25–29`, `config.py:415–427`.

Диагностика через `python config.py` маскирует поля, содержащие `token` или `key`. Поле `yt_oauth_client_secret` не соответствует этому условию и выводится целиком. Для остальных токенов выводятся первые восемь символов, хотя для диагностики достаточно наличия значения.

**Доказательство:** запуск CLI с временным config, содержащим только синтетический OAuth secret, вывел тестовую строку полностью. Реальные секреты не читались и не попадали в отчёт.

**Последствие:** копирование диагностики в issue или CI-log может раскрыть секрет. У installed-app OAuth client secret ограниченная защитная роль, поэтому это не доказательство самостоятельного захвата аккаунта; refresh token в этом воспроизведении не раскрывался.

**Исправление:** использовать существующий явный `_SECRET_FIELDS` как источник классификации и печатать только `configured`/`empty`, без префиксов. Добавить проверку каждого secret-поля, включая новые.

### A09. Быстрая отмена SSE фактически ждёт сетевое чтение

**Код:** `core/lm_client.py:326–413`, особенно `:404–413`.

Основной поток замечает отмену с периодом 0.5 секунды, но в `finally` синхронно вызывает `resp.close()`. Читающий поток в этот момент может держать блокировку buffered reader внутри `for raw_line in resp`. Закрытие ожидает это чтение; ограниченный `reader.join()` выполняется уже после блокирующего close и не ограничивает его длительность.

**Доказательство:** локальный сервер отправил HTTP/SSE-заголовки и молчал 2.5 с. Отмена установлена через 0.2 с. Метод вернулся через **примерно 2.51 с**, одновременно с закрытием соединения сервером, вместо ожидаемой проверки за ~0.5 с. Воспроизведение повторялось.

**Последствие:** при длинном socket timeout отмена и освобождение общей LLM-очереди задерживаются; может затянуться shutdown воркера. Аудит доказал задержку, но не воспроизвёл crash при закрытии окна, поэтому crash не объявляется установленным результатом.

**Исправление:** обеспечить неблокирующий для управляющего потока способ прерывания transport read: корректный socket shutdown/клиент с cancellable I/O либо единоличное владение чтением/закрытием и контролируемый срок остановки. Проверить, что отменённая генерация действительно освобождает сервер и очередь, а не только возвращает UI.

**Регрессия:** сервер прислал headers, но не SSE-строку; отмена должна вернуть управление в заданный бюджет и завершить reader. Добавить также отмену до headers и посреди генерации.

### A10. После удаления истории остаются связанные job_runs

**Код:** `core/history.py:62–82`, `core/history.py:702–738`.

`delete()` и `clear()` удаляют транскрипты, material texts, версии и bookmarks, но не `job_runs`. В этой таблице нет внешнего ключа с каскадным удалением. В ней остаются recipe, record_id, outcomes и сообщения ошибок.

**Доказательство:** во временной БД создан транскрипт с run. После `delete(record_id)` число записей `job_runs` осталось **1**; после `clear()` — также **1**.

**Последствие:** накопление сиротских записей и неполная семантика очистки. Это не утверждение о сохранении полного транскрипта в `job_runs`: сериализуются статусы и ошибки, не `StepOutcome.result`.

**Исправление:** удалять связанные run в той же транзакции либо мигрировать на согласованный FK/cascade с включённым enforcement. Отдельно документировать, что удаление записи из Library делает с экспортами, аудио и логами: их безопасное удаление — отдельная продуктовая политика.

### A11. Отменённый Insights-шаг записывает пригодный пустой кэш

**Код:** `core/insights.py:365–377`, `application/steps.py:522–545`, `application/job_engine.py:207–219`.

При отмене `generate_insight()` возвращает `[]`. `_insights_runner()` продолжает цикл, сохраняет все поля и манифест. Engine проверяет cancel перед runner, но не различает результат отменённого выполнения после возврата.

**Доказательство:** фиктивный клиент установил cancel во время первого запроса. Получены `cancelled=true`, outcome **`succeeded`**, все три поля JSON пусты, **`cache_valid=true`**.

**Последствие:** отмена способна заменить пригодные материалы пустыми и «отравить» следующий запуск кэшем. Registry отключает сигналы отменённого воркера, но это не прекращает запись файлов. Поэтому проблема существует и при отсутствии поздних UI-сигналов.

**Исправление:** определить единый явный результат отмены/исключение; проверять cancel перед каждой стадией и перед commit файлов. Engine должен отличать CANCELLED от SUCCEEDED/FAILED, но одной проверки engine после runner недостаточно — запись артефактов к этому моменту уже могла состояться. Нужен контроль отмены на границе commit.

**Регрессия:** отменить между стадиями и сразу перед записью; старый успешный файл/манифест должны сохраниться, новый пустой файл не должен попасть в кэш.

### A12. Содержимое артефакта обновляется неатомарно относительно манифеста

**Код:** `application/steps.py:156–158`, `application/steps.py:357–378`, `application/steps.py:678–710`, `infrastructure/persistence/artifact_store.py:69–78`.

JSON/Markdown результатов записывается через `Path.write_text()` непосредственно в финальный путь. Манифест атомарный, но остаётся от предыдущего результата при ошибке/аварии во время перезаписи. `is_cache_valid()` проверяет существование файла и совпадение старого ключа, не читаемость или content digest.

**Доказательство:** имитация частичной перезаписи существующего Insights JSON и `OSError` оставила `cache_valid=true`, хотя `load_artifact()` уже возвращал None из-за повреждённого JSON.

**Последствие:** предыдущий хороший результат потерян, а последующий запуск может пропустить генерацию и не загрузить ничего. Атомарность только manifest-файла не гарантирует целостность пары output/manifest.

**Исправление:** сначала записать и проверить новый результат во временный файл; использовать replace и согласованную стратегию фиксации манифеста. Надёжный вариант — версия/content-addressed файл плюс атомарный указатель на пару. В манифест включить digest/размер и проверять их при reuse. Отдельно обработать сбой между двумя заменами и одновременных писателей.

**Регрессия:** частичная запись, ошибка replace, crash между output и manifest; после сбоя доступен старый корректный результат либо принудительный cache miss, но не ложный hit.

## 5. Архитектура, безопасность и сопровождение

### Что стоит сохранить

- Qt-free DTO и application-координация позволяют проверять смысл операций без GUI. AST-тесты границ слоёв — полезный исполняемый архитектурный контракт.
- Разделение stub-unit и real-Qt suites принципиально правильно: обычные заглушки не проверяют queued signals, жизненный цикл QThread и остановку настоящих воркеров.
- `ModelRepository` проверяет скачанные файлы по размеру/SHA-256 и заменяет файл атомарно. Нельзя упрощать это до «скачалось без исключения».
- Конфигурация сохраняется через временный файл, fsync и replace; secret-bearing файл имеет POSIX 0600. OAuth использует loopback, state и PKCE; refresh token без keyring остаётся в памяти.
- HTTP/YouTube-адаптеры допускают инъекцию транспорта, времени и ожиданий. Это позволило воспроизвести ошибки протокола без внешних запросов и аккаунтов.
- В просмотренных subprocess-путях FFmpeg передаёт argv списком, без `shell=True`; глобального отключения TLS в просмотренных активных модулях не обнаружено. Это ограниченный результат просмотра, а не формальный сертификат безопасности.

### Где сосредоточен технический долг

| Файл | Строк | Практическое направление |
| --- | --- | --- |
| `ui/main_window.py` | 3 271 | Дальше отделять orchestration и состояние документа от виджетов; не делать массовый рефакторинг одновременно с P1-fix |
| `ui/youtube_panel.py` | 1 345 | Разделить редактируемый пакет, генерацию и отображение |
| `ui/transcript_view.py` | 1 308 | Развести модель редактирования, документ и UI-команды |
| `application/steps.py` | 1 296 | Вынести реализации шагов; реестр оставить декларативным, контракты успеха/отмены/кэша сделать общими |
| `core/history.py` | 1 104 | Централизовать транзакционные операции документа, версий и связанных runs |

Размер файла не объявляется самостоятельным дефектом. Но перечисленные области уже содержат несколько несовпадающих политик успеха, сохранения и восстановления. Приоритет — исправление этих контрактов с узкими регрессиями, затем декомпозиция.

Статический подсчёт обнаружил отсутствие return-аннотаций у 263 из 1 248 функций/методов `ui/`. Это не равно числу полностью непроверенных функций, однако поясняет ограничения заявления «mypy прошёл»: без `--check-untyped-defs` тела части неаннотированных функций проверяются ограниченно. Расширять типизацию стоит по границам состояния и протоколов, не количеством annotations ради метрики.

### CI и release: рекомендации, не доказанные runtime-дефекты

1. Добавить сценарные проверки по A01–A12, особенно policy boundary, resume-after-failure, cancel-before-commit, upstream invalidation и metadata change during upload.
2. Запускать SCA регулярно и при изменениях lock-файлов; хранить SBOM для frozen-пакетов, включающий нативные библиотеки.
3. Linux packaging использует минимальные bounds из `requirements.txt`, тогда как другие пути используют lock. Подготовить проверяемый Linux lock и явную матрицу платформ. В этом аудите не доказано, что конкретный release build сломан.
4. Закрепить GitHub Actions по immutable SHA, сузить permissions отдельных jobs и передавать workflow inputs в shell через env с валидацией. Workflow сейчас использует `@v4`/`@v2` и строковые inputs в shell; внешняя эксплуатация не установлена, workflow запускается вручную.
5. Проверять соответствие input release version и `pyproject.toml` перед сборкой. Описание input требует совпадения, но само описание не проверяет его.
6. Явно разграничить статус «история удалена» и «связанные файлы удалены». В частности, не обещать гарантированное безопасное стирание SQLite/WAL, экспортов и логов без отдельной реализации и проверки.
7. Актуализировать docstrings: например, заголовок `application/job_engine.py` ещё описывает engine как не подключённый к реальным генераторам и не имеющий persisted state, хотя интеграция и `run_store` уже есть. Исторический контекст лучше оставить в архиве.

## 6. Рекомендуемый порядок исправления

**Первая серия — конфиденциальность и корректность результата:** A01 и A07; затем A03/A11, чтобы ошибка и отмена не публиковали кэш как успешный. Для каждого изменения — отдельный небольшой commit и тест на нарушенный контракт.

**Вторая серия — восстановление и остановка:** A02 и A09. Проверять восстановление сохранённого run через реальный controller и отмену настоящего HTTP-stream, а не только заглушки методов.

**Третья серия — целостность и инвалидация:** A04/A05/A06/A12. Сначала определить полную идентичность входов, затем реализовать атомарную фиксацию и миграцию ключей. Иначе можно исправить один cache hit, сохранив ту же ошибку в соседнем слое.

**Четвёртая серия — зависимости и сопровождение:** A08/A10/A13/A14. Обновление urllib3 можно выполнять независимо и раньше, не ожидая рефакторинга.

Оценки в человеко-днях не приводятся: они потребовали бы выбора поддерживаемых платформ, стратегии transport cancellation и формата транзакционного хранения артефактов. Критерий завершения каждой серии — указанные регрессии плюс существующие gates, а не только отсутствие lint/type ошибок.
